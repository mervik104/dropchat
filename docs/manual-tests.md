# Ручные проверки DropChat

Автоматические тесты покрывают бизнес-логику, HTTP-контракты и компоненты UI.
Реальные WebRTC-соединения, Google Drive, Android WebView и особенности ОС
проверяются вручную по чек-листам ниже.

## Stage 0 — локальный каркас

1. Выполнить `npm ci`.
2. Выполнить `npm run typecheck`, `npm run lint`, `npm test`, `npm run coverage`.
3. В отдельном терминале запустить `npm run dev --workspace @dropchat/worker`.
4. Проверить `curl http://127.0.0.1:8787/api/hello` — ожидается
   `{"app":"DropChat","protocol":1,"runtime":"worker"}`.
5. Проверить `curl http://127.0.0.1:8787/api/health` — ожидается
   `{"ok":true,"app":"DropChat"}`; это подтверждает реальный локальный D1.
6. В отдельном терминале запустить `npm run dev --workspace @dropchat/web`.
7. Открыть `http://127.0.0.1:5173/` — ожидается заголовок DropChat и статус
   «Сервер доступен».
8. Остановить оба dev-сервера.

## Stage 1 — регистрация, auth, ip_group, /api/peers

1. Выполнить `cp worker/.dev.vars.example worker/.dev.vars`.
2. Выполнить `npm run db:migrate:local`.
3. Запустить Worker: `npm run dev --workspace @dropchat/worker`.
4. Выполнить `npm run smoke:stage1` — ожидается
   `Local peer discovery OK` и `Stage 1 smoke test passed.`
5. Проверить отсутствие токена:
   `curl -i http://127.0.0.1:8787/api/peers` — ожидается `401` и
   `{"error":"unauthorized"}`, без эха токена.
6. Зарегистрировать устройство вручную и убедиться, что ответ содержит профиль,
   но не содержит `secret`, `secret_hash` или `ip_group`.
7. Проверить preflight:
   `curl -i -X OPTIONS http://127.0.0.1:8787/api/devices -H 'Origin: http://localhost:5173' -H 'Access-Control-Request-Method: POST'`
   — ожидается `204` и `Access-Control-Allow-Origin: http://localhost:5173`.
8. Повторить preflight с `Origin: https://evil.example` — заголовок
   `Access-Control-Allow-Origin` должен отсутствовать.
9. Перезапустить Worker и повторить `npm run smoke:stage1` — регистрация и
   локальное обнаружение должны снова работать на сохранённой D1.
10. Остановить Worker.

## Stage 2 — web shell

1. Запустить Worker и web по инструкции из README.
2. Открыть `http://127.0.0.1:5173/` — должен появиться загрузочный экран, затем
   messenger shell с именем «Моё устройство».
3. Проверить в DevTools → Application → Local Storage ключ
   `dropchat.identity.v1`: там только `deviceId`, `secret`, `name`, `platform`.
4. Перезагрузить страницу — identity должна сохраниться, второй чат не создаётся.
5. Открыть настройки: отображаются имя устройства, платформа `web` и тема
   «как в системе».
6. Переключить системную тему macOS/Windows — интерфейс должен измениться без
   перезагрузки.
7. Сузить окно до мобильной ширины: список чатов и диалог должны быть разными
   экранами; после выбора чата доступна кнопка «Назад».
8. Проверить пустые состояния: «Рядом пока никого», «Пока нет чатов»,
   «Выберите чат».
9. Кнопка «Код приглашения» на Stage 2 должна быть disabled.

## Pre-Stage 3 — identity, настройки, WebSocket

1. Запустить Worker и web после `npm run db:migrate:local`.
2. В DevTools → Application → Local Storage открыть `dropchat.identity.v1`,
   изменить последний символ `secret` и перезагрузить страницу.
   Ожидается экран «Сервер не узнал устройство» без создания новой identity.
3. Проверить кнопки «Повторить», «Импортировать identity» и
   «Сбросить identity». После сброса создаётся новая identity.
4. В настройках изменить имя устройства и сохранить. После перезагрузки имя
   должно остаться новым (проверьте `PATCH /api/devices/me` в Network).
5. Нажать «Экспорт identity», скопировать текст, сбросить identity, затем
   вставить текст в «Импорт identity» и импортировать. Устройство должно
   восстановиться.
6. В консоли браузера выполнить `await navigator.storage.persisted()`; после
   запроса `persist()` браузер должен вернуть `true` или решение браузера
   (запрос best-effort).

## Stage 3 — WebSocket-тикеты и текстовые сообщения

1. Создать два связанных устройства. Пока нет UI приглашений, можно открыть
   два профиля браузера, взять `deviceId` из localStorage и вставить строку в
   локальную D1 (IDs должны быть отсортированы):
   `INSERT INTO peers (device_a, device_b, created_at) VALUES ('<меньший-id>', '<больший-id>', <timestamp>);`
2. Перезагрузить оба профиля — в «Чатах» должен появиться собеседник.
3. Открыть DevTools → Network → WS для одного профиля. Убедиться, что URL
   содержит только `?ticket=...`, без device secret.
4. Отправить текст из второго профиля: сообщение должно появиться у обоих без
   перезагрузки, у отправителя — сначала оптимистично.
5. Перезагрузить страницу — история сообщений должна сохраниться.
6. Отправить больше 50 сообщений и нажать «Загрузить ещё» — должна загрузиться
   предыдущая страница.
7. Закрыть вкладку одного профиля — у второго статус presence должен смениться
   на «не в сети»; открыть снова — «в сети».
8. Попробовать отправить пустое сообщение — запрос не должен уходить.
9. Проверить, что текст длиннее 4000 символов отклоняется сервером.

## Пред-Stage 4 — устойчивость и лимиты

1. Оборвать WebSocket (DevTools → Network → WS → Close) и убедиться, что клиент
   переподключается с нарастающей задержкой.
2. После переподключения проверить, что presence обновился, а пропущенные
   сообщения открытого чата догрузились.
3. Отправить сообщение с тем же `clientId` повторно (например, повторной
   кнопкой после ошибки) — в D1 и UI не должно появиться дубля.
4. Превысить лимит сообщений/тикетов/PATCH и проверить `429` + `Retry-After`.
5. Открыть два таба одного устройства: presence должен оставаться online, пока
   открыт хотя бы один WebSocket.
6. Остановить Hub/сетевой доступ к Durable Object во время отправки сообщения:
   HTTP-ответ на `POST` должен остаться успешным, сообщение — сохраниться.
7. Stage 7: cron должен очищать просроченные ws-тикеты (зафиксировано в README).

## Stage 4 — discovery, requests и invites

1. Открыть два браузера с одного публичного IP. Оба устройства должны появиться
   в «Рядом».
2. Нажать «Запрос» у второго устройства; во втором браузере появится запрос.
3. Нажать «Принять» — в «Чатах» обоих устройств появится собеседник.
4. Включить «Невидимый режим» в настройках одного устройства и проверить, что
   оно исчезло из «Рядом» у третьего устройства, но осталось в чатах у уже
   связанных.
5. Создать код приглашения на одном устройстве (5 минут), ввести его на
   удалённом устройстве — должна появиться связь.
6. Ввести неверный код 5 раз с одного устройства — шестая попытка должна
   вернуть `429`; после 10 минут окно сбрасывается.
7. Ввести просроченный/использованный код — ожидается `404`.
8. Убедиться, что чужой origin не может вызвать API, а секреты не попадают в
   ответы/URL.

Stage 7 cron должен очищать `ws_tickets`, `invite_failures`, просроченные invites
и peer_requests (см. README).

## Stage 5 pre-hardening — brute-force, блокировки, лимиты

1. Invite brute-force: с нескольких устройств одного `ip_group` ввести неверные
   коды. После `INVITE_IP_GROUP_FAILURE_LIMIT` (default 20/10 мин) новый redeem
   с этого IP должен вернуть `429`. Проверить сброс окна через 10 минут.
2. Глобальный предохранитель: распределить неверные попытки по разным IP.
   После `INVITE_GLOBAL_FAILURE_LIMIT` (default 100/10 мин) redeem должен
   вернуть `429` для всех. Проверить сброс по времени.
3. В меню чата нажать «Отвязать устройство» — чат исчезает, `GET/POST messages`
   возвращает `403`.
4. Заблокировать устройство: оно исчезает из «Рядом», не может отправить
   peer request и не может погасить invite.
5. Peer requests: превысить `PEER_REQUEST_LIMIT_PER_HOUR` (20/час) и
   `MAX_PENDING_PEER_REQUESTS` (10) — ожидать `429`.
6. Оставить запрос без ответа на `PEER_REQUEST_TTL_HOURS` (24 ч) — после TTL он
   исчезает из входящих, можно отправить новый.
7. Во втором устройстве принять invite/запрос — у создателя приглашения должно
   появиться заметное уведомление «Устройство X подключилось».

## Stage 5 — drive-gateway и реальный Google Drive

> Не отправляйте client secret/refresh token в чат. Для проверки используйте
> локальный `drive-gateway/.dev.vars`.

1. Запустить gateway напрямую (для curl):
   `npx wrangler dev -c drive-gateway/wrangler.jsonc --port 8788`
2. Взять `INTERNAL_KEY` из локального `.dev.vars` в переменную окружения, не
   печатая его.
3. Проверить квоту:
   `curl -s -H "X-Internal-Key: $INTERNAL_KEY" http://127.0.0.1:8788/health`
4. Создать сессию:
   `curl -s -X POST -H "X-Internal-Key: $INTERNAL_KEY" -H 'content-type: application/json' --data '{"size":5,"mime":"text/plain"}' http://127.0.0.1:8788/init`
   — в ответе только `sessionId`; URL Drive не должен появляться.
5. Загрузить 5 байт:
   `curl -s -X PUT -H "X-Internal-Key: $INTERNAL_KEY" -H 'Content-Range: bytes 0-4/5' --data-binary 'hello' http://127.0.0.1:8788/parts/<sessionId>`
   — ожидается `{"status":"done","driveFileId":"..."}`.
6. Скачать с Range:
   `curl -s -D - -H "X-Internal-Key: $INTERNAL_KEY" -H 'Range: bytes 0-1' http://127.0.0.1:8788/files/<driveFileId>`
   — ожидается `206`, `Content-Range`, `Accept-Ranges`.
7. Удалить:
   `curl -s -o /dev/null -w '%{http_code}' -X DELETE -H "X-Internal-Key: $INTERNAL_KEY" http://127.0.0.1:8788/files/<driveFileId>`
   — `204`; повторный DELETE также `204`.
8. Проверить, что `drive-gateway` не имеет публичного URL и не логирует токены,
   session URI и Drive URL.
9. Для service binding использовать одну команду:
   `npm run dev:workers` (gateway не должен открываться напрямую).

### Результат реальной проверки Stage 5 (2026-11-02)

Проверено локально против настоящего Google Drive (секреты не выводились):

1. `GET /health` → `200`, вернулись `quotaUsed` и `quotaLimit`.
2. `POST /init` → `201`, в ответе только `sessionId`; session URI и Drive URL
   отсутствовали.
3. `PUT /parts/:id` с `Content-Range: bytes 0-4/5` → `{"status":"done"}`,
   получен `driveFileId`.
4. `GET /files/:driveFileId` с `Range: bytes 0-1` → `200` (Google вернул полный
   5-байтный файл), `Accept-Ranges: bytes`, тело `hello`; контракт допускает
   `200` или `206`.
5. `DELETE /files/:driveFileId` → `204`; повторный DELETE → `204` (404
   трактуется как успех).
6. Токены, `INTERNAL_KEY`, session URI и Drive URL не печатались и не попадали
   в ответы.
