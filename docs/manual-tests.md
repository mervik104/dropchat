# Ручные проверки DropChat

Чек-лист для локальной и production-проверки. Секреты и токены не выводите в
терминал, логи и issue.

## Подготовка

```sh
npm ci
cp worker/.dev.vars.example worker/.dev.vars
cp drive-gateway/.dev.vars.example drive-gateway/.dev.vars
npm run db:migrate:local
```

Для облачных файлов заполните `drive-gateway/.dev.vars` по
[`google-cloud-setup.md`](google-cloud-setup.md).

Запуск:

```sh
npm run dev:workers
npm run dev --workspace @dropchat/web
```

Откройте <http://127.0.0.1:5173/> в двух разных браузерах или в обычном окне и
инкогнито. В двух вкладках одного профиля будет одна identity.

## Автоматические проверки

```sh
npm run typecheck
npm run lint
npm test
npm run coverage
npm run build
```

Ожидается 100% coverage во всех workspace и успешная production-сборка.

Smoke-проверки при запущенном Worker:

```sh
npm run smoke:discovery
npm run smoke:linking
```

- `smoke:discovery` регистрирует два устройства и проверяет секцию `local`.
- `smoke:linking` проверяет nearby request/accept и invite.

## Быстрый старт при плохой сети

1. Успешно открыть приложение и хотя бы раз загрузить список устройств.
2. Перезапустить страницу при медленном или недоступном Worker.
3. Убедиться, что UI открывается сразу с закешированными чатами, а не висит на
   экране загрузки.
4. Дождаться индикатора «Только локально» внизу слева, если сервер недоступен.
5. Открыть чат: локальные сообщения из `localStorage` должны отображаться.
6. При восстановлении сети индикатор исчезает, список устройств синхронизируется.

## Identity и авторизация

1. Открыть приложение в чистом профиле. В `localStorage` появляется
   `dropchat.identity.v1`.
2. Обновить страницу — identity и имя устройства сохраняются.
3. Запрос без `Authorization` к `/api/peers` возвращает `401`.
4. Изменить имя устройства в настройках — имя обновляется в шапке и в списке
   устройств у собеседника.
5. Включить «Невидимый режим» — устройство исчезает из «Рядом» у третьего
   устройства, но остаётся в чатах у уже связанных.
6. Экспортировать identity, сбросить локальные данные, импортировать строку
   обратно — устройство восстанавливается.
7. Проверить, что экспорт identity не показывается где-либо, кроме настроек.

## Обнаружение и связывание

1. Открыть два браузера на одном публичном IP с одинаковым хостом
   (`localhost` или `127.0.0.1`, не смешивать).
2. После загрузки обоих устройств обновить списки — они должны появиться в
   «Рядом».
3. Нажать «Запрос» у nearby-устройства; на втором появится входящий запрос.
4. Принять запрос — устройство появляется в «Чатах» у обоих.
5. Создать код приглашения на одном устройстве, применить на другом — связь
   появляется без nearby.
6. Проверить поиск по имени в списке и кнопку обновления списка.
7. Ввести неверный код приглашения 5 раз с одного устройства — шестая попытка
   должна вернуть `429`; окно сбрасывается через 10 минут.
8. Ввести использованный или просроченный код — ожидается `404`.
9. Отвязать устройство — оно исчезает из чатов, но может снова появиться в
   «Рядом», если не заблокировано.
10. Заблокировать устройство — оно исчезает из «Рядом», не может отправить
    запрос и не появляется во входящих.

## Текст и realtime

1. Открыть чат и отправить текст. Сообщение появляется оптимистично со статусом
   «Отправка…», затем подтверждается.
2. В сообщении должен быть виден транспорт: `локально` или `интернет`.
3. Проверить доставку второго устройства через WebSocket без обновления
   страницы.
4. Отключить Worker во время отправки — сообщение должно стать «Ошибка
   отправки»; кнопка «Повторить» повторяет с тем же `clientId` без дубля.
5. Открыть два таба одного устройства: presence остаётся online, пока открыт
   хотя бы один WebSocket.
6. Остановить Worker и снова запустить — клиент переподключается, обновляет
   presence и догружает пропущенные сообщения открытого чата.
7. Проверить пагинацию истории кнопкой «Загрузить ещё».
8. Проверить копирование текста сообщения.
9. Проверить, что очень длинный текст ограничен настройкой
   `MAX_MESSAGE_LENGTH` (по умолчанию 4000).

## Облачные файлы

Требуется настроенный `drive-gateway`.

1. Отправить файл 1–5 МБ в чат. Клиент сначала пробует P2P; при недоступном
   получателе должен сработать облачный fallback.
2. Проверить progress и отмену загрузки.
3. После завершения в сообщении видно «хранится 30 дней».
4. Скачать файл на втором устройстве по кнопке «Скачать».
5. Убедиться, что download идёт через Worker, а не напрямую с Google URL.
6. Проверить, что файл появляется в отдельной папке DropChat в Google Drive.
7. Проверить `401`/`403` на чужой файл или файл без связи.
8. Проверить превышение `MAX_FILE_SIZE` — ожидается `413`.
9. Проверить исчерпание квоты — ожидается `429` или понятная ошибка.
10. Проверить `GET /api/health/drive` с auth: возвращает `ok`, `quotaUsed`,
    `quotaLimit`.

## P2P и автоматический fallback

1. Открыть один и тот же чат на двух устройствах в одной сети.
2. Дождаться, пока клиент поднимет локальный DataChannel. Инициатор —
   устройство с меньшим `deviceId`.
3. Отправить текст — при открытом канале сообщение должно иметь транспорт
   `локально` и цвет локального сообщения.
4. Отправить файл 1–5 МБ — он должен уйти через WebRTC, в D1 остаётся только
   metadata (`transport=p2p`). На приёмнике файл скачивается через Blob.
5. Убедиться, что содержимое P2P-файла не запрашивается у Worker.
6. Отключить WAN/интернет, оставив Wi-Fi, при открытых вкладках:
   - текст должен продолжить идти через DataChannel;
   - файл в открытом чате должен передаться локально;
   - если metadata не сохранилась в D1, сообщение остаётся локальным.
7. Перезагрузить страницы — DataChannel пропадает; отправка без интернета
   должна завершаться ошибкой. Это ожидаемое ограничение.
8. Заблокировать STUN/WebRTC или остановить signaling — новый P2P-канал не
   должен подняться; файл в автоматическом режиме уйдёт в облако через 8 секунд.
9. Отменить P2P-передачу — DataChannel закрывается, частичный файл не должен
   сохраниться.
10. Проверить backpressure на большом файле: память браузера не должна резко
    расти.
11. На медленном канале отправить большой файл: после открытия DataChannel
    облачная загрузка не должна запускаться, даже если передача длится больше
    8 секунд. Повторных скачиваний/дублей быть не должно.

## Меню чата

1. Открыть меню «Действия с чатом».
2. Убедиться, что меню отображается поверх сообщений и не перекрывается ими.
3. Проверить «Отвязать устройство»: чат закрывается, список обновляется.
4. Проверить «Заблокировать устройство»: чат закрывается, устройство исчезает из
   «Рядом».
5. Смоделировать ошибку API для обоих действий — должно появиться уведомление,
   меню закрыться, приложение не падать.

## Настройки и UI

1. Проверить mobile/desktop раскладку, safe-area и скролл сообщений.
2. На телефоне открыть экранную клавиатуру — composer и поле ввода должны
   оставаться полностью видимыми, не уходя под клавиатуру.
3. Проверить автопрокрутку к новым сообщениям и поведение при чтении истории.
4. Проверить поиск по nearby, запросам и чатам.
5. Проверить пустые состояния: «Рядом пока никого», «Пока нет чатов»,
   «Сообщений пока нет».
6. Проверить ошибки загрузки identity и повторный retry.
7. Проверить, что кнопки недоступны во время busy/загрузки.
8. Проверить контраст текста и статусов в светлой и тёмной теме.
9. Проверить установку PWA: манифест и иконки доступны, приложение
   открывается в standalone-режиме. Полный offline-кеш пока не поддерживается.

## Retention и лимиты

1. Создать сообщение с `expires_at` в прошлом и вызвать retention:
   ```sh
   curl "http://127.0.0.1:8787/cdn-cgi/local/scheduled"
   ```
2. Убедиться, что просроченные сообщения и файлы удалены.
3. Проверить очистку `ws_tickets`, `invite_failures`, invites, peer_requests,
   endpoint/registration rate-limit rows.
4. Проверить abandoned upload: `uploading` старше 24 часов удаляется.
5. Превысить лимиты сообщений, тикетов, PATCH профиля и файлов — ожидается
   `429` с `Retry-After`.

## Production checklist

1. `GET /api/health` возвращает `200` и `{"ok":true,"app":"DropChat"}`.
2. CORS preflight с production origin возвращает `204` и
   `Access-Control-Allow-Origin`.
3. CORS preflight с чужим origin не возвращает `Access-Control-Allow-Origin`.
4. Gateway не имеет публичного URL.
5. GitHub Actions CI и Deploy Pages завершены успешно.
6. В задеплоенном JS нет секретов, Google-токенов и приватных ключей.
7. Связать два устройства через production UI и отправить текст и файл.
